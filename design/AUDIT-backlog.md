# Sinox API — لیست باگ‌ها و کارهای لازم، به ترتیب اهمیت

> این لیست از خواندن کد واقعی و اجرای کوئری روی `data/app.db` درآمده، نه حدس.
> هر مورد محل دقیقش در کد نوشته شده.
> هدف ظرفیتی که گفتی: **۱۵۰ تا ۳۰۰ کاربر همزمان**.

---

## 🔴 سطح ۰ — توقف‌کننده: بدون این‌ها ۳۰۰ کاربر همزمان سرور را می‌خواباند

این‌ها باگ ظاهری نیستند؛ معماری‌اند. اگر فقط همین چند مورد را حل کنی، بقیه‌ی
لیست وقت دارد.

### ۰-۱. جدول `usage_log` هیچ ایندکسی ندارد ← هر کوئری کل جدول را اسکن می‌کند

**تأیید شده با اجرای `EXPLAIN QUERY PLAN` روی دیتابیس خودت:**

```
SELECT * FROM usage_log WHERE user_id=? ORDER BY created_at DESC LIMIT 50
  → SCAN usage_log  +  USE TEMP B-TREE FOR ORDER BY

SELECT date(created_at), COUNT(*) FROM usage_log
  WHERE user_id=? AND created_at>=date('now','-6 days') GROUP BY 1
  → SCAN usage_log  +  USE TEMP B-TREE FOR GROUP BY

SELECT * FROM subscriptions WHERE user_id=? AND status='active' AND expires_at>datetime('now')
  → SCAN subscriptions
```

جدول `subscriptions` هم روی `user_id` ایندکس ندارد — و این کوئری **در مسیر داغ
هر درخواست `/v1/chat/completions`** اجرا می‌شود (`routes/proxy.js:70` و `:81`).

الان `usage_log` سه هزار و پانصد ردیف دارد و در ۱۲ روز پر شده، یعنی حدود ۳۰۰
ردیف در روز با چند کاربر. با ۳۰۰ کاربر فعال این عدد روزانه به ده‌ها هزار
می‌رسد و ظرف چند ماه از یک میلیون ردیف رد می‌شود.

**چرا کشنده است:** `better-sqlite3` **همگام (synchronous)** است. هر کوئری
event loop نود را کامل قفل می‌کند. اسکن یک جدول یک‌میلیونی یعنی چند صد
میلی‌ثانیه فریز کامل سرور — برای **همه‌ی** ۳۰۰ کاربر، نه فقط آن یک نفر.

**کار لازم:**
```sql
CREATE INDEX idx_usage_user_time   ON usage_log(user_id, created_at DESC);
CREATE INDEX idx_usage_key         ON usage_log(key_id);
CREATE INDEX idx_usage_model_time  ON usage_log(model, created_at);
CREATE INDEX idx_subs_user_status  ON subscriptions(user_id, status, expires_at);
CREATE INDEX idx_subs_status       ON subscriptions(status);
CREATE INDEX idx_orders_user       ON orders(user_id, created_at DESC);
CREATE INDEX idx_card_user         ON card_orders(user_id, created_at DESC);
CREATE INDEX idx_crypto_user       ON crypto_orders(user_id, created_at DESC);
```
این ارزان‌ترین و بزرگ‌ترین برد کل لیست است. چند ثانیه اجرا، چند برابر ظرفیت.

### ۰-۲. داشبورد در لود اول ۱۱ درخواست همزمان می‌فرستد

`public/dashboard.html` (بلوک `DOMContentLoaded`):

```js
loadActiveSub(); loadPlans(); loadSubscriptions(); loadKeys();
loadUsage(); loadUsageSummary(); loadTickets(); loadFAQ();
loadInvoices(); loadProfile(); initKeyModal();
```

همه‌ی بخش‌ها با هم لود می‌شوند، درحالی‌که کاربر فقط **یک** بخش را می‌بیند و
بقیه `display:none` هستند.

**حساب کن:** ۳۰۰ کاربر × ۱۱ درخواست = **۳۳۰۰ درخواست همزمان** روی یک دیتابیس
همگام. سه‌تای آن‌ها (`/api/user/usage`، `/usage/summary`، `/usage/daily`) دقیقاً
همان کوئری‌های اسکن‌کننده‌ی بند ۰-۱ هستند.

**کار لازم:** لود تنبل — هر بخش فقط موقع باز شدن دیتایش را بگیرد، و نتیجه کش
شود تا سوییچ دوباره درخواست جدید نزند. فقط `loadActiveSub` و `loadProfile` در
لود اول لازم‌اند.

### ۰-۳. `bcryptjs` همگام، روی رشته‌ی اصلی

`routes/auth.js:48, 79, 166, 190, 193` و `server.js:412, 698`:

```js
bcrypt.compareSync(password, user.password)
bcrypt.hashSync(password, 10)
```

`bcryptjs` پیاده‌سازی **خالص جاوااسکریپت** است (نه ماژول نیتیو). با cost=10 هر
عملیات حدود ۸۰ تا ۱۵۰ میلی‌ثانیه CPU خالص روی event loop می‌گیرد. یعنی سرور در
آن مدت هیچ کار دیگری نمی‌کند.

اگر ۵۰ نفر همزمان لاگین کنند، صف می‌شوند: نفر پنجاهم چند ثانیه منتظر می‌ماند و
در همان مدت **کل ترافیک `/v1` هم متوقف است**.

**کار لازم:** به نسخه‌ی نیتیو `bcrypt` مهاجرت کن و از API غیرهمگام
(`await bcrypt.compare(...)`) استفاده کن. اگر نصب ماژول نیتیو دردسر دارد،
حداقل از API کال‌بکی خود `bcryptjs` استفاده کن که کار را تکه‌تکه می‌کند.

### ۰-۴. سقف نرخ `/v1` برای مشتری واقعی خیلی پایین است

`server.js:112-131`:

```js
v1IpLimiter  → max: 25 در دقیقه، بر اساس IP
v1KeyLimiter → max: 10 در دقیقه، بر اساس کلید API
```

دو مشکل جدی:

۱. کاربری که پکیج ۲۰۰۰ ریکوستی خریده، فقط می‌تواند **۱۰ درخواست در دقیقه**
   بزند. برای کسی که Claude Code یا یک ایجنت وصل کرده، این عملاً یعنی سرویس
   کار نمی‌کند. مشتری فکر می‌کند سرویس خراب است.
۲. محدودیت IP (۲۵ در دقیقه) در ایران فاجعه است: چند کاربر پشت یک NAT اپراتور
   یا یک شبکه‌ی شرکتی، **سهمیه‌ی همدیگر را می‌خورند**. یک نفر پرمصرف بقیه را
   قطع می‌کند.

**کار لازم:** سقف کلید را به مقدار واقعی و منطقی ببر (مثلاً ۶۰ تا ۱۲۰ در
دقیقه، یا بر اساس تیر پکیج متفاوت باشد)، و محدودیت IP را روی `/v1` یا بردار یا
خیلی بالا ببر — چون احراز هویت آنجا با کلید انجام می‌شود نه IP. محدودیت IP را
برای `/api/auth` نگه دار که جایش همان‌جاست.

### ۰-۵. تک‌پروسه بودن + نبود فشرده‌سازی

- `server.js:1022` فقط `app.listen` — یک پروسه، یک هسته. با DB همگام، یک هسته
  سقف کل ظرفیت توست.
- هیچ middleware فشرده‌سازی (`compression`) وجود ندارد. `admin.html` حجمش
  **۱۵۴ کیلوبایت** و `dashboard.html` **۷۵ کیلوبایت** است و خام سرو می‌شوند.
  با gzip این‌ها به یک‌پنجم می‌رسند.

**کار لازم:** `compression` را اضافه کن (یا روی Caddy فعالش کن). برای
چندپروسه‌ای شدن با SQLite در حالت WAL می‌شود چند پروسه‌ی خواننده داشت، ولی
قبلش حتماً ۰-۱ و ۰-۲ را حل کن — احتمالاً بعد از آن‌ها اصلاً نیازی نباشد.

### ۰-۶. `db.prepare()` داخل هر هندلر، به‌جای یک‌بار در بالای فایل

در سراسر `routes/proxy.js`، `payment.js` و بقیه، `db.prepare(...)` **داخل**
تابع هندلر صدا زده می‌شود. یعنی SQLite هر بار دستور را از نو کامپایل می‌کند.
در مسیر `/v1` که پرترافیک‌ترین مسیر است، این هزینه‌ی بی‌دلیل تکرار می‌شود.

**کار لازم:** همه‌ی `prepare`ها را به سطح ماژول ببر و فقط `.get()/.run()/.all()`
را داخل هندلر صدا بزن.

### ۰-۷. نبود سیاست نگهداری برای جدول‌های در حال رشد

- `usage_log` بی‌نهایت رشد می‌کند و هیچ‌وقت خلاصه یا آرشیو نمی‌شود.
- `captcha_challenges` فقط موقع **تأیید موفق** پاک می‌شود (`routes/auth.js:24`).

**کار لازم:** یک کرون شبانه که کپچاهای منقضی را پاک کند، و برای `usage_log` یک

خلاصه بخوانند. لاگ خام را مثلاً ۹۰ روز نگه دار.

## 🟠 سطح ۱ — باگ‌های پولی و باگ‌هایی که کاربر مستقیم می‌بیند

### ۱-۱. خرید با موجودی، مسابقه‌ی شرطی دارد ← موجودی منفی می‌شود

`routes/payment.js` در `/api/payment/balance-checkout`:

```js
const user = db.prepare('SELECT balance FROM users WHERE id = ?').get(req.user.id);
if (user.balance < plan.price) return res.status(400).json({...});
db.prepare('UPDATE users SET balance = ROUND(balance - ?, 4) WHERE id = ?').run(plan.price, req.user.id);
const created = createSubscription(req.user.id, plan);
```

این الگوی «اول بخوان، بعد عمل کن» است، **بدون تراکنش و بدون شرط اتمیک**. اگر
کاربر دو تب باز کند و همزمان بزند (یا دوبار کلیک کند)، هر دو درخواست از شرط رد
می‌شوند، هر دو کسر می‌کنند، و **دو اشتراک** ساخته می‌شود با موجودی منفی.

جالب اینکه خودت در `PROJECT-HANDOFF.md` بند ۸ نوشته‌ای «quota فقط با UPDATE
اتمیک» — و برای سهمیه واقعاً رعایت شده (`proxy.js:90`)، ولی **برای پول
رعایت نشده**.

**کار لازم:**
```js
const paid = db.prepare(
  'UPDATE users SET balance = ROUND(balance - ?, 4) WHERE id = ? AND balance >= ?'
).run(plan.price, req.user.id, plan.price);
if (paid.changes === 0) return res.status(400).json({ error: 'موجودی کافی نیست' });
```
و کل کسر + ساخت اشتراک + ثبت تراکنش داخل یک `db.transaction()`.

### ۱-۲. شماره‌ی فاکتور تکراری تولید می‌شود

`server.js:372-379`:

```js
function getNextInvoiceNumber() {
  const z    = MAX(order_id) FROM orders
  const c    = MAX(order_id) FROM crypto_orders
  const card = MAX(order_id) FROM card_orders
  return max >= 1000 ? max + 1 : 1001;
}
```

دو مشکل:

۱. **بدون قفل و بدون یکتایی.** دو چک‌اوت همزمان همان عدد را می‌گیرند. با ۳۰۰
   کاربر این قطعی است، نه احتمالی. نتیجه: دو فاکتور با یک شماره — کابوس
   حسابداری و پشتیبانی.
۲. سه بار `MAX(CAST(...))` روی سه جدول **بدون ایندکس** — یعنی سه اسکن کامل در
   هر چک‌اوت.

**کار لازم:** یک جدول شمارنده‌ی مستقل (یا یک کلید در `settings`) با افزایش
اتمیک داخل تراکنش، به‌علاوه‌ی `UNIQUE` روی `order_id` هر سه جدول.

### ۱-۳. ستون مبلغ فاکتورها واحدهای مختلف را قاطی کرده

سرور در `/api/user/invoices` سه جدول را UNION می‌کند و هرکدام واحد متفاوتی دارد:

| منبع | فیلد | واحد واقعی |
|---|---|---|
| `orders` (زرین‌پال) | `o.amount` | تومان |
| `crypto_orders` | `c.amount_usdt` | **تتر** |
| `card_orders` | `c.amount_rial` | **ریال** |

و در `dashboard.html` هر سه زیر یک ستون با عنوان **«مبلغ (تومان)»** چاپ می‌شوند:

```html
<td>${formatNumber(inv.amount)}</td>
```

یعنی یک فاکتور ۱۷ دلاری کریپتو، عدد «۱۷» را زیر عنوان «تومان» نشان می‌دهد. این
همان چیزی است که گفتی بخش فاکتورها مشکل دارد.

**کار لازم:** سرور یک فیلد `currency` هم برگرداند و UI واحد را کنار هر ردیف
بنویسد. ضمناً ریال و تومان را هم یکی نکن.

### ۱-۹. لیست تیکت ادمین: ستون بدون نام ← شمارنده‌ی پاسخ‌های خوانده‌نشده مرده است

`routes/tickets.js:69-72`:

```sql
SELECT t.*, u.username, u.email,
  (SELECT COUNT(*) FROM ticket_messages m WHERE m.ticket_id = t.id) msg_count,
  (SELECT COUNT(*) FROM ticket_messages m WHERE m.ticket_id = t.id
     AND m.sender='user' AND m.created_at > t.updated_at)      ← بدون AS
FROM tickets t JOIN users u ON t.user_id = u.id WHERE 1=1
```

زیرکوئری دوم **هیچ نام مستعاری ندارد**. SQLite اسم ستون را متن خام خودِ عبارت
می‌گذارد، پس فرانت به‌هیچ‌وجه نمی‌تواند با یک نام تمیز بخواندش. عملاً این
شمارنده مرده است.

بدتر: منطقش هم غلط است. شرط `m.created_at > t.updated_at` هیچ‌وقت درست نمی‌شود،
چون `updated_at` در **همان لحظه‌ی ثبت پیام** به now() آپدیت می‌شود
(`tickets.js:52` و `:99`). یعنی حتی با نام درست هم همیشه صفر برمی‌گرداند.

**کار لازم:** یک ستون واقعی `last_read_admin_at` / `last_read_user_at` به جدول
`tickets` اضافه کن و «خوانده‌نشده» را نسبت به آن حساب کن.

یعنی اگر کاربری ایمیلش را غلط وارد کند یا رمزش را گم کند و SMTP هم کار نکند،
ادمین **هیچ کاری نمی‌تواند بکند**.

**کار لازم:** `PUT /api/admin/users/:id` برای ویرایش،
`POST /api/admin/users/:id/reset-password` برای ریست دستی، و یک حذف نرم
(soft delete) — حذف سخت اطلاعات مالی را خراب می‌کند، پس `deleted_at` بگذار و
از لیست‌ها فیلترش کن.

---

### ۲-۲. دو مکانیزم موازی برای یک کار

`POST /api/admin/users/:id/ban` (در `server.js:705`) و
`POST /api/admin/users/:id/deactivate` (در `routes/users.js:59`) **هر دو**
`is_banned` را ست می‌کنند، ولی `deactivate` علاوه بر آن کلیدها و اشتراک‌ها را هم
غیرفعال می‌کند. دو دکمه در پنل، دو رفتار متفاوت، یک اسم مبهم.

**کار لازم:** یکی را نگه دار، دومی را حذف کن، و در UI دقیق بنویس هرکدام چه
می‌کند.

---

### ۲-۳. بخش‌های گمشده‌ی پنل ادمین

- اندپوینت `GET /api/admin/transactions` وجود دارد ولی **هیچ بخشی در UI** برایش
  نیست. یعنی گزارش مالی نوشته شده ولی دیده نمی‌شود.
- هیچ بخشی برای دیدن `usage_log` سراسری نیست — ادمین نمی‌تواند بفهمد کدام مدل
  خطا می‌دهد یا کدام کاربر غیرعادی مصرف می‌کند.
- هیچ صفحه‌ی «سلامت مسیرها» نیست، درحالی‌که `model_routes` ستون‌های
  `fail_count`، `last_error` و `disabled_until` را دارد و پر می‌شوند.

## 🟢 سطح ۳ — کمبودهای محصولی

### ۳-۱. ایمیل کار نمی‌کند

`nodemailer` در `package.json` هست ولی طبق `PROJECT-HANDOFF.md` بند ۱۰، SMTP
فعال نیست و کد بازیابی رمز فقط از پنل ادمین خوانده می‌شود. یعنی:
- کاربری که رمزش را فراموش کند باید در تلگرام پیام بدهد
- هیچ ایمیل تراکنشی نداریم (فاکتور، هشدار انقضا، پاسخ تیکت)

### ۳-۲. هیچ هشدار پیش‌دستانه‌ای وجود ندارد

کاربر وقتی می‌فهمد سهمیه‌اش تمام شده که کدش خطای ۴۰۳ گرفته. نه ایمیلی، نه
اعلانی، نه هشداری در ۸۰٪ مصرف یا ۳ روز مانده به انقضا. برای یک سرویس فروش این
مستقیماً یعنی از دست دادن تمدید.

### ۳-۳. پیام‌های خطای انگلیسی در رابط فارسی

نمونه‌ی مشخص، `routes/payment.js` در ساخت کلید:
```js
return res.status(403).json({ error: 'You need an active subscription with remaining quota to create an API key' });
```
این متن مستقیم به کاربر فارسی‌زبان نشان داده می‌شود. چند مورد مشابه دیگر هم در
`payment.js` و `proxy.js` هست (`Plan not found`, `Payment not configured yet`).

### ۳-۴. متغیرهای CSS تعریف‌نشده

در `public/css/style.css` سه متغیر استفاده شده‌اند ولی **هیچ‌جا تعریف نشده‌اند**:
`--surface` (۶ مورد) · `--secondary` (۱ مورد) · `--error` (۱ مورد).

اثر واقعی‌شان:
- کارت‌های صفحه‌ی مقالات پس‌زمینه ندارند و شفاف‌اند
- گرادیانت کارت موجودی داشبورد نصفه است (`dashboard.html`، `var(--secondary,#7c3aed)`)
- حباب پیام تیکت در داشبورد پس‌زمینه ندارد (`dashboard.html:1351`)
- بج «پرفروش» کارت قیمت گرادیانت شکسته دارد

این را می‌شود در سه خط حل کرد و باید همان اول ریدیزاین انجام شود.

## ⚪ سطح ۴ — بهبود و پاکسازی

- `getSetting()` (`server.js:496`) در هر فراخوانی به دیتابیس می‌زند و کش ندارد؛
  در مسیر پرداخت چند بار پشت سر هم صدا زده می‌شود. یک کش درون‌حافظه‌ای با
  ابطال روی `setSetting` کافی است.
- `reconcileSubscriptions()` هر ۵ دقیقه سه UPDATE با اسکن کامل می‌زند؛ با
  ایندکس روی `subscriptions(status)` حل می‌شود.
- `/api/user/usage` سقف ۲۰۰ ردیف دارد ولی صفحه‌بندی ندارد — کاربر نمی‌تواند
  تاریخچه‌ی قدیمی‌تر را ببیند.
- `formatNumber` روی مبالغ اعشاری کریپتو (`17.0231`) گرد می‌کند و دقت را از بین
  می‌برد.
- هیچ تستی در پروژه نیست. حداقل برای مسیر پول (کسر موجودی، idempotency پرداخت،
  اتمیک بودن سهمیه) چند تست لازم است — این‌ها جاهایی‌اند که باگ = ضرر مالی.

## یک نکته درباره‌ی تست ظرفیت

قبل از اینکه به ۳۰۰ کاربر برسی، حتماً با یک ابزار بار (مثل `autocannon` یا `k6`)
این دو سناریو را جدا تست کن:

۱. **۲۰۰ لود همزمان داشبورد** — این event loop را با کوئری‌های سنگین می‌زند.
۲. **۲۰۰ درخواست همزمان `/v1/chat/completions`** — این مسیر داغ و سهمیه را می‌زند.

اگر بعد از اعمال ۰-۱ و ۰-۲ زمان پاسخ p95 زیر ۳۰۰ میلی‌ثانیه ماند، تک‌پروسه
جواب می‌دهد و لازم نیست معماری را عوض کنی.
